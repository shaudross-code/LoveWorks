# RCA — Web Push "Send test" fails in production (labor-admin-hub)

**Symptom:** Tapping "Send test" in the push status panel never delivers a web push; the test silently fails.

## Root cause (PROVEN)
The production secret **`VAPID_PRIVATE_KEY` holds a corrupt / invalid value** that pywebpush cannot parse. Backend logs (active run `4703e29b`) show, on every `POST /api/push/test` and `POST /api/push/subscribe`:

```
server - WARNING - webpush error: Could not deserialize key data. The data may be in an
incorrect format ... Details: ASN.1 parsing error: invalid length
```

`send_web_push()` catches this, logs a warning and returns — so `/api/push/test` still responds `200 OK` while sending nothing. That is why the test "fails"/never arrives.

### Why it's the stored prod value, not the code
- I pulled preview's `backend/.env` into a sandbox and ran the **exact code path** (`VAPID_PRIVATE_KEY.replace("\\n","\n")` → `load_pem_private_key`). The preview key loads cleanly: `ECPrivateKey, curve secp256r1 (P-256)`. **Code is correct.**
- `list_secrets(equals=...)` against prod: `VAPID_PRIVATE_KEY` → **`matches_expected: false`** — the prod value is NOT the known-good preview PEM. Combined with the ASN.1 deserialize error, the stored prod value is malformed/truncated or was re-pasted incorrectly in the Secrets tab (likely the `\n` / PEM body got mangled). Custom secrets carry forward from the previous prod run (not re-seeded from preview), so a bad edit persists across redeploys.

## Answers to the 5 checks
1. **VAPID env present?** All three exist and are non-empty.
   - `VAPID_PUBLIC_KEY`: matches preview — `GET /api/push/public-key` returns the same key `BM8kDGdHKnf...` with **`available: true`**. ✅
   - `VAPID_PRIVATE_KEY`: present but **does not match preview** (`matches_expected:false`) and **cannot be deserialized**. ❌ ← the blocker
   - `VAPID_SUBJECT`: present but **differs** from preview's `mailto:admin@loveworks.com` (`matches_expected:false`). Not the current blocker (deserialize fails first) but verify it is a valid `mailto:` once the key is fixed, or Apple/FCM may reject the JWT.
2. **pywebpush installed (PUSH_AVAILABLE)?** Yes. `public-key` returns `available:true`, and execution reaches `webpush()` far enough to attempt VAPID key deserialization — PUSH_AVAILABLE is true.
3. **Backend logs:** Repeated `webpush error: ... ASN.1 parsing error: invalid length` tied to each `/api/push/test` and `/api/push/subscribe`. **No** Apple/FCM HTTP status codes (403/400/413) because the failure happens *before* any HTTP call to the push endpoint — during key load. Separately observed: `fcm send failed: Invalid APNs credential` — that is the **native FCM/APNs path (FIREBASE_*)**, a distinct issue from web push, not the reported symptom.
4. **prod Mongo `push_subscriptions`:** 5 **active** subscriptions (Apple `web.push.apple.com` + FCM web endpoints), including recent ones created 04:24–04:27 during testing. **None were flipped to `is_active=false`** — the deserialize exception throws before any HTTP send, so no 404/410 pruning occurred. Subscriptions are healthy.
5. **`/sw.js`:** Served correctly — `200`, `content-type: application/javascript`, real service-worker content (not the React index.html). ✅

## Fix (ENV, not code)
**User action:** In Deployment Panel → Secrets, set **`VAPID_PRIVATE_KEY`** to the exact valid PEM from preview `backend/.env` — the P-256 private key that pairs with the already-correct `VAPID_PUBLIC_KEY` — preserving the literal `\n` escape sequences (the code converts `\n`→newline at load). Do not strip/alter the base64 body. While there, confirm **`VAPID_SUBJECT`** is a valid `mailto:` (e.g. `mailto:admin@loveworks.com`). Then redeploy.

No code change is required — `backend/server.py` handling is correct.

(Secondary, separate from this report: the native-FCM `Invalid APNs credential` warnings indicate the Firebase/APNs credential for native push needs attention — track independently.)
